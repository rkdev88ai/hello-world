Client Lifecycle Management platform for Ready to Transact

Target architecture for onboarding, servicing and offboarding corporate and institutional clients across 50+ markets, built on four foundational capabilities.

RTT visionOnboard and service clients so that they are enabled to transact with the bank at the earliest.
Policy enginePolicies become versioned OPA rules with full lineage OrchestrationSegment-specific journeys, parallel by default, visible in real time External dataTrusted sources, resolved to one entity ID, served by API Client dataJSON LEM and domain objects, cleanly separated from case data

1Architecture overview

Layered view: channels on top, journey services in the middle, data and systems of execution below. Foundations are colour-coded.

Figure 1. Logical architecture of the CLM platform. Numbers in CLM services refer to the 14 journey capabilities.

Layers

  • Channels: every entry point (client, RM, ops, partner API, forms) lands on the same journey, never a side process.
  • Orchestration: owns the journey; services own the work.
  • CLM services: stateless domain microservices, one per capability, each a System of Record for its domain object.
  • Client data: case store vs master stores, separated by a commit gate.

Interaction patterns

  • Commands: orchestrator to services over synchronous APIs.
  • Facts: services publish domain events via outbox to the event mesh.
  • Decisions: every service and the orchestrator ask the local OPA sidecar; no policy logic in code.
  • Reference data: services read entity data from EDP APIs, never directly from vendors.

Design principles

  • Ask the client only for what policy requires and EDP cannot supply.
  • Parallel by default; sequence only on true data dependency.
  • Provision early, activate on approval.
  • Every decision traceable to a policy clause and data source.
  • Regional data planes for residency; one logical platform.

2RTT journey flow

The 14 capabilities arranged as three concurrent tracks. Dashed boxes are conditional stages.

Figure 2. Target journey. Accounts are pre-staged once product scope is known and activated when KYC is approved.

Know track

  • Intake captures minimum identifiers only (name, country, reg. no. or LEI, products, booking entity).
  • EDP pre-fills the entity profile, ownership and officers.
  • OPA computes the delta: required data and docs minus what is already held.
  • One consolidated outreach request; repeat loops only for genuinely new gaps.

Assess track

  • Tax, regulatory classification, UBO and screening run in parallel.
  • Regulatory classification (MiFID, EMIR, Dodd-Frank etc.) triggered only for FM products.
  • Risk rating waits on UBO and screening outcomes (true dependency).
  • EDD inserted dynamically when the risk rating is medium or high.

Enable track

  • Accounts created in TP systems in a restricted state while KYC is in progress.
  • Limits and SSIs set up in parallel with assessment.
  • Activation is one orchestrated step that lifts all restrictions together.
  • Offboarding reverses the track: restrict, unwind, close, update status.

4Policy engine

Converts Group onboarding policy, country addenda and regulatory documents into versioned, testable OPA rules, with lineage from clause to decision.

Policy-to-rule pipeline

Components

  • Policy library: versioned source documents with clause-level IDs.
  • Obligation catalogue: atomic, canonical requirements (one obligation, one testable statement).
  • Rule authoring: decision tables for policy SMEs; Rego generated, not hand-written, for most rules.
  • Test harness: opa test plus golden scenarios per client type and market.
  • Bundle registry: signed, semver bundles with effective-from dates.
  • Distribution: bundle server pushes to OPA sidecars beside each CLM service.
  • Decision logs: every evaluation logged with input hash, bundle version and result.

Decision services exposed

  • journey/route: stages applicable to client type, market, product.
  • kyc/requirements: data and document requirements, with acceptable alternatives.
  • tax/obligations, reg/classification_required
  • ubo/threshold: ownership threshold by jurisdiction.
  • risk/edd_trigger, review/frequency
  • product/eligibility: can this client get this product here.
  • lifecycle/restrictions: what to block on restrict or exit.

Lineage and versioning

Figure 3. Each decision traces back to the clause that caused it. Example values are illustrative.

Versioning rules

  • Bitemporal: effective date (when policy applies) separate from published date.
  • Open cases pin the bundle version they started on; policy decides whether to re-evaluate.
  • Country addenda layered on Group policy: stricter rule wins unless an approved waiver exists.
  • Every rule change carries its obligation ID; no orphan rules allowed (CI check).

Sample rule (Rego)

package kyc.docs

# OBL-0412 | Group v7.2 §4.3 | SG addendum v3.1 §2.1
required[doc] {
  input.client.type == "LOCAL_CORPORATE"
  input.booking.country == "SG"
  not held("BOARD_RESOLUTION")
  doc := {"code": "BOARD_RESOLUTION",
          "obligation": "OBL-0412"}
}

held(code) {
  some d in input.evidence
  d.code == code; d.status == "VERIFIED"
}

How it accelerates RTT

  • Right first time: the full requirement list is known at intake, so the client is asked once.
  • Asks only for the gap: rules evaluate against data already held and EDP-sourced data.
  • Policy change without code change: new country rules go live as a bundle, in days not releases.
  • Impact analysis before go-live prevents surprise rework on in-flight cases.
  • Explainable decisions shorten QA, audit and regulator queries.

5Orchestration

A central journey orchestrator that composes segment-specific journeys at runtime, runs them durably across systems, and records every transition for real-time and point-in-time views.

Journey composition

  • Templates are assembled from reusable stage blocks, not copied flows.
  • Template chosen by client type; tasks inflated by OPA for market and product.
  • Re-planning: a new fact (e.g. high risk) adds stages to a running journey.
  • Templates are versioned and deployed independently of services.

Execution

  • Durable state survives restarts; every step idempotent.
  • Provisioning as a saga: per-TP steps with retry, compensation or parked ops task.
  • Human tasks routed to work queues by skill, market and SLA.
  • Correlation: one journey ID across all systems and events.

Journey 360

  • Live: stage, owner, blockers, SLA clock, next action, for RM and client.
  • Point-in-time: replay the event store to any timestamp for audit or dispute.
  • Portfolio view: all journeys by segment, market, stage, ageing.
  • Process mining on events to find bottlenecks.

How it accelerates RTT

  • Parallel tracks replace sequential hand-offs; elapsed time follows the critical path only.
  • Pre-provision and activate pattern removes account set-up from the critical path.
  • Segment templates avoid over-processing simple clients and under-processing complex ones.
  • Real-time visibility removes chasing and status calls; RMs and clients see the same truth.
  • SLA timers and escalation stop cases stalling silently.

6External data platform

One governed gateway to global data vendors and 50+ country registries, resolving every external record to the bank's entity ID and serving it to CLM through APIs.

Figure 5. EDP pipeline from source to API.

Name and ID resolution with Splink

Figure 6. Probabilistic matching (Fellegi-Sunter) with a human review band. Thresholds tuned per market.

Components

  • Connector framework: pluggable adapters per source; rate limits, cost and licence tracking.
  • Raw zone: immutable payloads, kept for evidence and replay.
  • Canonical entity model: identifiers, names (incl. transliterations), addresses, officers, shareholders, filings, status.
  • Entity resolution: Splink on Spark for batch, DuckDB for on-demand single-entity matches.
  • ID crosswalk: LE ID to BvD ID, LSEG PermID, S&P ID, LEI, registry numbers, with confidence and method.
  • Monitoring: subscribes to source changes; emits events for event-driven review.

APIs to CLM

  • GET /entities/{leId} golden view with field provenance
  • POST /resolve name + attributes to candidate matches
  • GET /entities/{leId}/ownership graph
  • Events: EntityChanged, OwnershipChanged

Governance

  • Licence entitlements enforced per consuming use case.
  • Data stays in-region where registry terms or local law require.
  • Source quality scorecards per market.

Operating model

  • Central team owns connectors and resolution models.
  • Country teams own registry mappings and precedence.
  • New registry onboarded as configuration plus one adapter.

How it accelerates RTT

  • Pre-fill: most entity data arrives before the client is contacted, shrinking outreach.
  • Registry-sourced data is accepted as evidence where policy allows, removing document requests.
  • Reliable ID resolution prevents duplicate clients and repeated KYC across businesses.
  • Ownership chains from vendors give UBO analysis a head start.
  • Change events trigger targeted refresh instead of full periodic reviews.

7Client data

Legal Entity Master plus domain data objects, stored as versioned JSON documents in their System of Record, with case data held separately until committed.

Figure 7. Case data is a working copy; only the commit gate writes to master objects. SoR assignments shown are indicative.

Modelling rules

  • One JSON Schema per object, held in the schema registry; backward-compatible evolution.
  • LEM holds identity only; domain facts live in domain objects linked by LE ID.
  • Each object has exactly one SoR; others read via API or events.
  • Bitemporal versions: validFrom (business) and recordedAt (system).
  • Field-level provenance: source, method, evidence reference.
  • Hierarchies (parent, branch, fund-to-manager) as typed relationships.

How it accelerates RTT

  • Reuse: a client already known in one market or business is not re-collected; only the delta is asked for.
  • TP systems receive clean, approved data once, cutting account-set-up rejects.
  • JSON objects evolve with new markets and products without schema migrations across systems.
  • Clear SoR ownership ends reconciliation between CLM, credit and TP copies.
  • Committed changes publish events, so downstream systems update in minutes, not batches.

Suggested RTT measures

  • Time to RTT (intake to first transaction possible), by segment.
  • Outreach rounds per case.
  • Share of fields pre-filled from EDP.

  • QA rework rate.

  • Policy change lead time (clause to live rule).
  • Time to onboard a new registry.

9Cross-cutting concerns

Data residency

  • Regional data planes (e.g. EU, APAC, Middle East, Americas) with in-country stores where mandated.
  • Global index holds only permitted identifiers.
  • OPA rules also govern cross-border data access.

Audit & lineage

  • Immutable journey events, decision logs and master versions.
  • Reconstruct any client view and any decision as at any date.

Security

  • Attribute-based access by role, market, segment, data class.
  • Field-level encryption for identity documents and PII.
  • mTLS service mesh; signed policy bundles.

Resilience

  • Durable workflows survive outages; TP calls retried with backoff.
  • OPA sidecars keep last good bundle if distribution fails.
  • EDP caching shields journeys from vendor downtime.

Observability

  • Trace per journey ID across services and TP adapters.
  • SLOs on decision latency, enrichment latency, provisioning success.

AI governance

  • LLM clause extraction and IDP outputs always human verified before use.
  • Model inventory, validation and drift monitoring for risk and matching models.
