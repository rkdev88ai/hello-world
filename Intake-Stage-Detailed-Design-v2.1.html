Stage 1 — Intake: Detailed Design (v2.1)

Redesigned intake flow of fourteen steps: sequential scoping (IN-01…03), a five-track parallel evidence build (IN-04…08), a convergent assessment path (IN-09…10), and a human-verified, closed-loop client interaction cycle (IN-11…14) that iterates until the document checklist has zero gaps — each step classified as human, API/STP, deterministic rules, or agentic.

ScopeIntake stage only
Entryprospect.qualified event (CRM)
ExitIN-10 gap set empty → Gate G1
StatusDraft for architecture review
SECTION 01

Execution & Dependency Model

The orchestrator instantiates the twelve steps with the following precedence constraints. Everything not explicitly ordered runs as early as its inputs allow — the requirement graph, not a hard-coded sequence, is what the Case Orchestrator executes.

ConstraintRuleOrchestration mechanics
Sequential headIN-01 → IN-02 → IN-03 strictly in order.Each step's completion event releases the next. IN-03 (scope) is the trigger that lets the Policy Engine size the rest of the stage.
Parallel fan-outIN-04, IN-05, IN-06, IN-07, IN-08 all start on IN-03 completion.Five independent tracks; each fails, retries, and completes on its own. IN-08 is instantiated only if Financial Markets products are in the IN-03 scope.
Soft inputIN-05 is informational only — it never blocks anything. But if its ownership data is available when IN-07 runs (or arrives while IN-07 is open), it must be consumed as an input.Modelled as an optional data subscription: IN-07 subscribes to ownership.draft.updated; late-arriving ownership facts trigger an incremental re-assessment of sanctions nexus within IN-07, never a stage rework.
Assessment joinIN-09 starts only when IN-04, IN-06 and IN-07 are all complete. IN-05 and IN-08 never gate IN-09.AND-join on three completion events. IN-08 joins the flow later, at IN-10, where its questionnaire requirements enter the outreach pack.
Convergent tailIN-10 after IN-09; then IN-11 → IN-12 sequentially. IN-11 requires human verification before anything is dispatched.IN-10 waits for IN-08's output if IN-08 was instantiated and is still running (the only case where IN-08 delays anything). IN-12 fires only on the IN-11 approval fact.
Client loopIN-12 → IN-13 (monitor for client response) → IN-14 (enrich from returned information) → back to IN-10 for a fresh gap check. The loop repeats until the gap set is empty.IN-13 is a standing listener (channel webhook + mailbox polling fallback), not a queued task. Each IN-14 completion re-runs IN-10 as an incremental gap check; a non-empty gap set produces a delta outreach (only the still-missing items, via IN-11's human verification again); an empty gap set exits the loop and hands the case to Gate G1. Loop-count and elapsed-time guards escalate stalled cases to the RM.

Stage exit is now the loop's exit condition, not a dispatch event: the stage completes when an IN-10 gap check returns an empty set — everything the policy checklist demands is evidenced, including client-verified data. Gate G1 then evaluates on a fully closed checklist rather than on "we've asked the client", which materially raises the quality of what Tax, Enrich and KYC inherit.

SECTION 02

Step-Level Design

StepName & what happensTypeExecution detailHuman touchpoint / exception
IN-01CRM prospect received. Consume prospect.qualified from CRM; open the case; return the case ID for bidirectional status sync.API / STPEvent subscription on the mesh; schema-validated payload (legal name, country of incorporation, registration identifiers if known, owning RM, opportunity products); idempotent case creation keyed on CRM opportunity ID so replays never double-create.None. Malformed payloads are rejected back to CRM with a machine-readable reason code; nothing lands in a human queue.
IN-02Entity resolution & de-duplication. Match the prospect against the internal client master and in-flight cases. Outcomes: new entity / existing client (route to extend-scope flow) / duplicate in-flight case (merge).HybridDeterministic first pass on strong keys (LEI, registration number, tax ID). Unmatched records go to the Entity Resolution agent, which scores fuzzy candidates (name variants, transliterations, group hierarchy membership) with cited evidence per candidate. Auto-merge only above the policy-set confidence threshold; the match decision is written to the ledger as a resolution fact with its evidence.Below-threshold matches → data steward picks from the ranked, evidence-backed candidate list (accept / reject / new entity). SLA-clocked; steward decision feeds back as agent training signal.
IN-03Jurisdiction & product scoping. RM confirms the markets where the client will be served and the product set (cash, FX, derivatives, trade finance, secured lending…). This is the step that sizes the entire remainder of the stage — the five parallel tracks are instantiated from its output.HumanRM Workbench task with an agent-drafted scope proposal: the client's operating footprint (from CRM + any early data) × the bank's network coverage × cross-sell patterns of comparable clients. Policy Engine validates the chosen combination inline (unsupported market/product pairs blocked with the reason shown). On confirmation, scope.confirmed releases IN-04…08 and the Policy Engine derives the stage's requirement graph.RM decision is the step. If the RM defers, SLA escalation to the team lead; scope changes later in the stage trigger a targeted re-plan (delta tracks only), not a restart.
IN-04Data enrichment (external sources). Retrieve company registry extracts, GLEIF/LEI, credit bureau & corporate hierarchy data (D&B or equivalent), KYC-utility profiles for every in-scope market; reconcile into a proposed golden record.API / STP + AgenticParallel connector calls with per-source retries and circuit breakers; raw payloads hashed into the Evidence Vault. The reconciliation agent then aligns attributes across sources (legal name, status, addresses, industry codes) with per-attribute citations and confidence; source-precedence rules come from the Policy Engine, not the agent.Material conflicts (e.g., "dissolved" status in one source) → data steward with the agent's side-by-side comparison. Source outages leave the requirement open and tracked — never silently skipped.
IN-05Initial ownership structure (informational). Build a first-pass ownership tree — likely ≥10% owners and intermediate holdings — from registry filings, annual reports, and vendor hierarchy data. Not a gate for anything in this stage; verification happens in Enrich.AgenticOwnership Unwrap agent recursively processes filings; every ownership edge is citation-backed with a confidence score; thresholds and stop conditions are computed deterministically by the Policy Engine. Publishes ownership.draft.updated events as the tree grows — which IN-07 subscribes to for sanctions-nexus assessment. Opaque layers (bearer shares, trusts) are recorded as open items for Enrich, with drafted client questions.None in-stage — deliberately. Whatever is unresolved becomes an Enrich-stage requirement and (where client input is needed) an item in the IN-10 outreach pack.
IN-06Adverse media & sanctions view. Assemble the raw external risk picture: submit the company and known parties to sanctions and PEP screening, and pull adverse media coverage for the past 24 months.API / STPBatch submission to screening providers through the gateway; list versions and query timestamps recorded for audit; the 24-month media window enforced at query time. Output is the unassessed alert/article set plus clean-result facts — assessment deliberately lives in IN-07, keeping data-gathering (repeatable, cheap) separate from judgement (audited).None. Zero-alert results write a clean screening fact directly; provider outage keeps the requirement open with automatic resubmission.
IN-07Initial screening & assessment. Assess everything IN-06 gathered: entity-match plausibility, materiality, and financial-crime relevance per alert; compute sanctions nexus (ownership/control links to sanctioned entities) using IN-05's ownership data whenever available; disposition hits.HybridThe Adverse Media agent produces a triage pack per alert — match rationale, discriminators (DOB, geography, identifiers), source credibility, cited summary, and a draft recommendation. Deterministic discriminator rules may auto-close obvious false positives; the agent alone never closes anything. Nexus computation is a deterministic traversal of the available ownership tree against sanctions lists (OFAC 50%-style rules); it re-runs incrementally on each ownership.draft.updated event, and its output records which ownership snapshot it used.Surviving alerts → Compliance Cockpit for disposition with the triage pack attached (typed outcomes: false positive / true — proceed with EDD flag / true — recommend exit; 4-eyes on true hits). A true hit here can trigger early exit before the bank spends full due-diligence effort.
IN-08Regulatory classification applicability (conditional). If IN-03 scoped any Financial Markets products (FX, derivatives, securities), determine which trading/markets regimes apply and what counterparty classifications must be established — e.g., EMIR FC/NFC+/NFC− and clearing thresholds, Dodd-Frank US-person and ECP status, MiFID II client categorisation, plus APAC OTC regimes (MAS, HKMA, JFSA) per booking market.Rulesregclass.applicability(scope, entityProfile) on the Policy Engine: booking jurisdictions × FM products × entity attributes → the set of applicable regimes, the classifications to be evidenced, and the client questionnaires/representations required (e.g., ISDA-style classification letters). Output extends the requirement graph and feeds the IN-10 outreach pack. The step only determines applicability and requirements; the classifications themselves are evidenced and confirmed downstream once client responses arrive.None in the happy path — pure rules. Regime combinations the rulebook doesn't cover raise a policy-gap exception to the onboarding design authority (a rulebook fix, not a case workaround).
IN-09Preliminary risk assessment. On completion of IN-04 + IN-06 + IN-07, compute the initial client risk score: country, industry, product, ownership-complexity, channel, and screening-outcome factors.RulesDeterministic scoring model in the Policy Engine over the reconciled golden record and screening dispositions; output includes factor-level contributions and sets the diligence tier — which deepens or lightens the document checklist that IN-10 evaluates. Uses IN-05's ownership view opportunistically for the complexity factor (present = scored; absent = defaulted conservatively and flagged).None — preliminary by design. The accountable Client Risk Assessment with human sign-off remains a KYC-stage step.
IN-10Policy comparison & outreach preparation. Compare everything gathered against the policy-derived document/data checklist for this scope and risk tier; identify every gap; assemble a single consolidated client outreach pack.Rules + AgenticGap analysis is deterministic: checklist items from requirements.derive() (including IN-08's questionnaire requirements, and IN-05's unresolved-ownership questions) minus evidenced items = the gap set, each gap traceable to the rule that demands it. The Narrative agent then drafts the client-facing outreach content — why each item is needed, in plain language, in the client's correspondence language — from those rule-linked gaps. One pack per case; never per-department requests. On loop re-entry from IN-14, the gap check runs incrementally against the newly evidenced items: a non-empty result produces a delta outreach containing only the still-missing or newly-triggered items; an empty result raises intake.checklist.complete and exits the stage to Gate G1.Onboarding officer reviews the outreach pack before it proceeds (accuracy of the ask, tone, client sensitivities) — a 2-minute review of a drafted pack, not an hour of assembly. Waits for IN-08 only when IN-08 was instantiated and is still open. Loop-count and elapsed-time guards escalate cases stuck in the cycle to the RM.
IN-11Client verification summary + human verification. Compose the summary of (a) information gathered — the profile the bank has built, for the client to verify — and (b) information required — the gap set from IN-10 — as one coherent, channel-ready package. A human verifies the package before anything reaches the client.Agentic + HumanNarrative agent composes strictly from ledger facts; every "we hold this about you" statement is linked to its source; required items carry the plain-language rationale from IN-10. Rendered per channel (portal structured view + PDF); prefilled verification responses where the bank's data can be confirmed with one click. The verification task presents the exact client-facing rendering with per-statement provenance one click away; approval writes an outreach.approved fact (with the approver and the pack's content hash) that IN-12 requires before dispatch. Edits made during verification are captured as corrections, not free-text overwrites — so the agent's drafting improves from them. On loop iterations, delta packs go through the same verification with a side-by-side diff against the previously approved pack.Mandatory human verification — onboarding officer (or RM for sensitive relationships, flaggable at IN-03) approves, edits, or rejects the pack. Nothing is ever sent to a client without a named approver on the ledger. Reject returns the pack to the agent with the reviewer's reasons; SLA-clocked with escalation.
IN-12Dispatch approved pack. Send the human-approved pack to the client through the scoped channel (portal invitation, secure e-mail fallback) and schedule the chaser cadence.API / STPDispatch fires only on the outreach.approved fact and sends exactly the approved content hash — no post-approval mutation possible. Delivery receipts and open-tracking land on the ledger; chaser cadence and escalate-to-RM thresholds are policy parameters; chasers reference the original pack rather than generating new asks.Client-side only. RM is notified (not tasked) when chasers exhaust — preserving the relationship touch for genuine stalls.
IN-13Monitor client response. Keep listening for the client's submission: event-driven receipt through the channel when the client submits via portal, with mailbox polling as the fallback for e-mail/attachment responses.API / STPA standing listener, not a queued task: channel webhook (client.submission.received) as the primary path; scheduled mailbox polling (secure-mail/shared-mailbox connector) as fallback, with sender-and-reference matching to bind inbound items to the right case and requirement. Partial submissions are accepted and processed item-by-item — the loop doesn't wait for a complete response. Every receipt is acknowledged back to the client automatically; attachments are virus-scanned and hashed into the Evidence Vault on arrival.None in the happy path. Unmatchable inbound items (wrong reference, unknown sender) route to an ops triage queue rather than being dropped; chaser escalation from IN-12 remains the stall-handling mechanism.
IN-14Enrich from client-returned information. Process everything the client sent — verified/corrected profile data, completed questionnaires, and uploaded documents. PDFs and scans are read agentically; extracted data updates the case and closes requirements. Then loop back to IN-10 for a fresh gap check.AgenticDoc Intelligence agent classifies each document (which requirement it satisfies, which form family, which version), then extracts fields with per-field confidence and source-page citations; structured portal responses bypass extraction and land directly as evidence facts. Client corrections to bank-held data ("that address is wrong") update the golden record and trigger targeted re-runs of only the steps whose inputs changed (e.g., a corrected registration number re-fires IN-06 screening). Completion raises enrichment.applied, which re-enters IN-10.Low-confidence extractions → targeted human verification of only those fields (never full re-keying). Documents that don't satisfy the requirement they were sent for (wrong doc, expired, unsigned) are marked with a specific defect code so the next IN-11 delta pack explains precisely what to fix.

Net human footprint of the stage: one RM scoping decision (IN-03), exception-only steward touches (IN-02, IN-04), compliance disposition only for surviving alerts (IN-07), and a mandatory verification of every client-bound pack (IN-11) — nothing reaches a client without a named approver on the ledger. Every other step is machine-executed with full provenance, and the client loop (IN-12…14 → IN-10) runs hands-free until it either closes the checklist or trips a loop-count/time guard to the RM. The client is touched through one coherent thread — a verification pack and, at most, targeted delta requests that explain exactly what's still needed and why.
