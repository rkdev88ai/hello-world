CLMT — Intake Stage
Detailed Technical Design

Component architecture, integration contracts, workflow implementation, case-level data objects (per task IN-01…IN-14), and the intake-stage domain data model (Entity.Definition, Entity.Identifiers, Entity.Associations, Entity.Documents) — on the mandated stack: React · Kong · Camunda 8 · Drools · PostgreSQL · LangGraph.

SECTION 01

Technology Stack & Key Decisions

ConcernSelectionRole in the intake stage
UIReact 18 + Workbench BFF (Node/NestJS)Case workbench for CM/Ops/Compliance; embeds Camunda Tasklist tasks via the Tasklist GraphQL/REST API; task forms are React components bound to the case-task JSON objects in §5.
API gatewayKong Gateway (ingress + egress)Ingress: the CLMT process API for CRM (POST /onboarding/v1/prospects), the channel submission callback, and the workbench BFF route — OAuth2 client-credentials, mTLS, rate-limiting, schema validation plugins. Egress: single controlled exit for every external call (client master, external data platform, screening, checklist, SerpAPI, LLM) with per-upstream credentials, retries and circuit-breaking — so external integrations are governed in one place.
Workflow engineCamunda 8 (Zeebe) — chosen over Temporal, rationale belowExecutes clmt-intake-v1 BPMN: the sequential head, the parallel fan-out with the AND-join, human tasks (Tasklist), the client-response message catch, chaser timers, and the IN-14 → IN-10 loop.
Rules engineDrools (KIE Server) + DMNIN-04 data-validation rule sets, match-confidence routing thresholds (IN-02), checklist dedupe and gap computation (IN-10), chaser cadence policy. Rules are versioned KIE containers; every evaluation returns fired-rule IDs into the task object for audit.
DatabasePostgreSQL 16Two schemas: clmt_case (master case + case tasks; task payloads as JSONB modelled 1:1 on the §5 objects) and clmt_domain (the Entity.* domain tables of §6). Document binaries in S3-compatible object storage; Postgres holds metadata + hashes.
Agentic runtimeLangGraph (Python/FastAPI service)Three graphs: adverse-media-search (IN-06, SerpAPI tools), outreach-drafting (IN-11), doc-extraction (IN-14). The service hosts Zeebe job workers, so agent steps are ordinary service tasks to the engine — with model/prompt versions and citations written back into the task object.
Identity & secretsBank IdP (OIDC) + VaultWorkbench SSO via OIDC; service-to-service OAuth2 CC minted at Kong; external API credentials held in Vault, injected into Kong egress upstreams — never in service config.

1.1  Camunda 8 vs Temporal — why Camunda for this stage

CriterionCamunda 8Temporal
Human tasks (IN-02×2 verifications, IN-03 scope entry, IN-11 approval)Native. Tasklist with forms, claims, candidate groups, escalation — exactly the maker/checker machinery this stage needs.Build-your-own: signals + a custom task inbox service. Significant custom code for four human touchpoints.
Message correlation (IN-13 client submission)Native message catch events correlated on caseId; publish from the submission API or mailbox poller.Signals — equivalent capability, code-defined.
Timers / chasers / loop guardsBoundary timer events (non-interrupting chasers; interrupting escalation) declared on the model.Durable timers — equivalent, in code.
Auditability & governanceBPMN diagram = the reviewable artefact. Ops, audit and regulators read the same model the engine executes; Operate gives per-instance visual state.Execution history is complete but code-shaped; needs tooling to present to non-engineers.
Agentic sub-flowsDelegated to LangGraph inside the agent service — the engine sees one job per agent step.Genuinely stronger for code-first, long agent orchestration.

Decision: Camunda 8 (self-managed) executes the case spine, because this stage is dominated by human tasks, message correlation, timers, and audit-facing process governance — all native to Camunda. The agentic work stays in LangGraph where code-first orchestration belongs, invoked as Zeebe jobs. (If the bank later standardises on Temporal for engineering reasons, the §5 task objects and §6 domain model carry over unchanged — the coupling to the engine is confined to worker adapters.)

SECTION 03

Workflow Implementation — clmt-intake-v1

One BPMN process per master case. Task-to-element mapping below; every service task is a Zeebe job with a typed job type, retried with backoff, and idempotent via a key derived from (caseId, taskId, attempt).

StepBPMN element(s)Job type / formNotes
IN-01Start: process instance created by Case Mgmt Svc on POST /prospects → service task create-master-casecase.createCase row + Entity.Definition seed written before instance start so the process always references a persisted case.
IN-02Service task client-master-search → user task verify-cm-matches → XOR gateway → [certain match] service task link-and-close → end event (case closed) / [no match] service task external-name-resolution → user task verify-ext-matchesclientmaster.search · form F-IN02A · edp.resolve · form F-IN02BHuman verification is mandatory on both checks — even a "perfect" API match is confirmed by a person before linking or accepting external IDs. Drools supplies the ranking thresholds shown in the form.
IN-03User task capture-scopeform F-IN03 (CM group)Jurisdictions + products; on complete, sets process variables that drive the IN-08 conditional flow and all downstream API payloads.
—Parallel gateway (fork) — five outgoing flows—IN-08 flow has a condition: hasFMProducts = true; otherwise that token skips to its join.
IN-04Service task edp-fetch-profiles → business rule task validate-profile (Drools)edp.profile.fetch · rules.validateOne fetch per resolved external ID; validation results (per-rule pass/fail) land in the task object and on screen.
IN-05Service task edp-fetch-ownershipedp.ownership.fetchWrites Entity.Associations; sets ownershipAvailable variable consumed by IN-07's payload builder (soft input — no sequence dependency).
IN-06Service task agent-adverse-mediaagent.adversemedia (agent svc worker)LangGraph graph: plan queries → SerpAPI search → filter/dedupe → summarise with links → "nothing found" verdict when empty. Long-poll job with heartbeat; timeout + retry safe (idempotent run key).
IN-07Service task name-screeningscreening.submitPayload = entity + any ownership associations available at execution time (from IN-05 if done). Returns upfront sanctions/PEP indication into the task object.
IN-08Service task regclass-determine (conditional flow)regclass.determineOutput = classifications to perform (MiFID, Dodd-Frank, …) + questionnaires — consumed by IN-10's checklist merge.
—Parallel join A = IN-04 + IN-06 + IN-07 → IN-09 service task client-risk-assessment → Parallel join B = (IN-09 path) + IN-05 + IN-08 tokenscra.assessMatches the approved dependency model: IN-05/IN-08 never gate IN-09; all tokens converge before IN-10.
IN-10Service task doc-checklist-fetch → business rule task dedupe-and-gap (Drools) → XOR gateway: [no gaps] → end event stage-complete / [gaps] → IN-11checklist.fetch · rules.gapGap rule: items satisfiable by already-sourced external data are auto-marked SATISFIED_BY_EXTERNAL_DATA (no document evidence needed); remainder require evidence. Loop counter increments on each entry.
IN-11Service task agent-draft-outreach → user task verify-outreach → XOR: [rejected] back to draft / [approved] proceedagent.outreach.draft · form F-IN11Approval writes approver + SHA-256 content hash into the task object; IN-12 dispatches that exact hash.
IN-12XOR by channel: service task dispatch-channel or dispatch-email; non-interrupting boundary timers for chasers on the following catch stateoutreach.channel · outreach.emailChaser cadence parameters from Drools policy; chasers reference the original pack.
IN-13Intermediate message catch event client-submission, correlation key = caseId; interrupting boundary timer → RM escalation user task on stallmessage published by Case Mgmt Svc (channel API) or Mailbox PollerPartial submissions re-publish the message per batch; the catch is re-armed inside the loop so multiple deliveries are consumed.
IN-14Service task agent-extract-enrich → sequence flow back to IN-10agent.extractLangGraph doc-extraction graph per document; low-confidence fields spawn a targeted user task verify-extraction before enrichment applies. Loop guard: loopCount > N or elapsed > T → escalation path.

6.2  PostgreSQL implementation (DDL extract)

-- ============ clmt_case ============
CREATE TABLE clmt_case.onboarding_case (
  case_id            text PRIMARY KEY,
  case_type          text NOT NULL,
  stage              text NOT NULL,
  status             text NOT NULL,
  entity_ref         text NOT NULL REFERENCES clmt_domain.entity_definition(entity_ref),
  client_master_id   text,
  source             jsonb NOT NULL,              -- {system, opportunityId, relationshipManager}
  risk_rating        char(1) CHECK (risk_rating IN ('A','B','C','D','E')),
  loop_count         int  NOT NULL DEFAULT 0,
  process_instance_key bigint,
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX ux_case_crm_opp ON clmt_case.onboarding_case ((source->>'opportunityId'));

CREATE TABLE clmt_case.case_task (
  task_id      text PRIMARY KEY,
  case_id      text NOT NULL REFERENCES clmt_case.onboarding_case(case_id),
  task_code    text NOT NULL,                     -- IN-01 … IN-14
  task_type    text NOT NULL,                     -- API | RULES | AGENTIC | HUMAN | HYBRID
  status       text NOT NULL,
  payload      jsonb NOT NULL,                    -- §5 object ("data" + envelope fields)
  started_at   timestamptz, completed_at timestamptz,
  UNIQUE (case_id, task_code, (payload->'data'->>'iteration'))
);
CREATE INDEX ix_task_case   ON clmt_case.case_task (case_id, task_code);
CREATE INDEX ix_task_payload ON clmt_case.case_task USING gin (payload jsonb_path_ops);

CREATE TABLE clmt_case.outreach_request (
  outreach_id  text PRIMARY KEY,
  case_id      text NOT NULL REFERENCES clmt_case.onboarding_case(case_id),
  iteration    int  NOT NULL,
  mode         text NOT NULL CHECK (mode IN ('CHANNEL','EMAIL')),
  content_sha256 text NOT NULL,                   -- equals approved hash from IN-11
  approved_by  text NOT NULL, approved_at timestamptz NOT NULL,
  dispatched_at timestamptz, delivery_status text
);

CREATE TABLE clmt_case.client_submission (
  submission_id text PRIMARY KEY,
  case_id       text NOT NULL REFERENCES clmt_case.onboarding_case(case_id),
  received_via  text NOT NULL CHECK (received_via IN ('CHANNEL_API','MAILBOX_POLL')),
  received_at   timestamptz NOT NULL,
  items         jsonb NOT NULL                    -- [{requirementCode, documentRef|value, sha256}]
);

-- ============ clmt_domain ============
CREATE TABLE clmt_domain.entity_definition (
  entity_ref     text PRIMARY KEY,
  legal_name     text NOT NULL,
  legal_form     text,
  incorporation_country char(2) NOT NULL,
  incorporation_number  text NOT NULL,
  incorporation_date    date,
  operating_status      text,
  industry       jsonb,                           -- {scheme, code, description}
  nature_of_business text,
  addresses      jsonb NOT NULL DEFAULT '[]',     -- source-attributed array
  risk_rating    jsonb,                           -- {value, scale, band, assessedBy, sourceTask}
  lineage        jsonb NOT NULL,
  UNIQUE (incorporation_country, incorporation_number)
);

CREATE TABLE clmt_domain.entity_identifier (
  entity_ref  text NOT NULL REFERENCES clmt_domain.entity_definition(entity_ref),
  scheme      text NOT NULL,                      -- CLIENT_MASTER | LEI | MOODYS_ID | IHS_MARKIT_ID | SWIFT_KYC_ID | UEN_SG …
  id_value    text,
  status      text NOT NULL,                      -- VERIFIED | PENDING | NOT_LINKED
  source      text, verified_by text, source_task text,
  PRIMARY KEY (entity_ref, scheme)
);

CREATE TABLE clmt_domain.entity_association (
  assoc_id    text PRIMARY KEY,
  entity_ref  text NOT NULL REFERENCES clmt_domain.entity_definition(entity_ref),
  party       jsonb NOT NULL,                     -- {name, type, country}
  role        text NOT NULL,                      -- SHAREHOLDER | ULTIMATE_OWNER | DIRECTOR …
  pct         numeric(5,2),
  direct      boolean NOT NULL DEFAULT true,
  via_assoc   text REFERENCES clmt_domain.entity_association(assoc_id),
  source      text NOT NULL, evidence_doc text, source_task text NOT NULL,
  screening   jsonb                                -- {pepPossible, sanctionsPossible, screeningRef}
);

CREATE TABLE clmt_domain.entity_document (
  document_ref text PRIMARY KEY,
  entity_ref   text NOT NULL REFERENCES clmt_domain.entity_definition(entity_ref),
  origin       text NOT NULL CHECK (origin IN ('EXTERNAL_SOURCE','CLIENT','BANK')),
  channel      text,
  doc_type     text NOT NULL,
  satisfies    text,                              -- requirement code from IN-10
  storage_ref  text NOT NULL,                     -- S3 URI (WORM bucket)
  sha256       text NOT NULL,
  received_at  timestamptz NOT NULL,
  classification_confidence numeric(4,3),
  source_task  text NOT NULL
);
CREATE INDEX ix_doc_entity ON clmt_domain.entity_document (entity_ref, doc_type);

Modelling stance: the §5 task objects live as JSONB — they are working records whose shape evolves with the process, and GIN indexing covers workbench queries. The Entity.* domain data is relational-first (typed columns, FKs, uniqueness on scheme/ID pairs) because it outlives the case, feeds downstream stages, and is what the bank's client data model consumes. The source_task column on every domain row is the lineage thread back to the exact task object — and its audit block — that produced the value.
