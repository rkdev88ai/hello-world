Beyond BPMN: Deterministic and Probabilistic Agentic Orchestration

How to replace workflow-centric execution with stateful, policy-bound agents without sacrificing determinism, auditability, resilience or regulatory control.
Thesis. The future bank should not encode business processes primarily as BPMN diagrams executed by workflow engines. It should encode goals, state, obligations, policies and capabilities in an agentic runtime. Deterministic requirements remain deterministic code and policy. Probabilistic models are used only where the problem itself is probabilistic.

1. Executive position

The bank can adopt agents as the primary orchestration abstraction without turning regulated processes into LLM-driven improvisation. The key is to separate the system into a deterministic control plane and a probabilistic intelligence plane.

Deterministic

Control plane

State transitions, eligibility, mandatory sequencing, segregation of duties, limits, jurisdiction rules, timeouts, retries, approvals, entitlements, policy versioning, transactional writes and evidence retention.

Probabilistic

Intelligence plane

Document interpretation, entity matching, adverse-media assessment, classification, narrative generation, exception analysis, summarisation and tool selection where multiple valid actions may exist.

The decisive design choice: deterministic requirements must never become deterministic merely because the prompt says “always”. If a requirement is a control, it belongs in code, policy-as-code, schemas, authorization, transaction boundaries or graph topology — not in an LLM instruction.

This leads to a different definition of an enterprise agent. An agent is not necessarily “an LLM with tools.” It is a bounded, stateful execution unit with a goal, an allowed action set, a contract, a policy envelope and an auditable lifecycle. Some agents contain no language model at all. These deterministic agents replace many BPMN service tasks, gateways, timers and sub-processes with ordinary software functions and explicit graph transitions. Other agents invoke frontier models, but only behind typed interfaces and deterministic gates.

What changes strategically

“Agentic” should describe the execution architecture, not the degree of randomness.

2. Why move beyond BPMN

BPMN solved an important problem: a standardized notation bridging business process design and implementation. The Object Management Group (OMG) continues to publish BPMN 2.0.2 as the formal specification. That notation remains useful for communicating high-level process intent. The architecture argument in this paper is narrower: BPMN should stop being the strategic runtime programming model for complex, adaptive banking processes.

2.1 The scaling problem is combinatorive

Consider corporate onboarding. Routing depends on legal-entity type, domicile, booking jurisdictions, product set, customer segment, ownership complexity, tax status, regulatory classification, sanctions/PEP findings, documentary evidence, risk tier, outsourcing restrictions and data residency. BPMN represents combinations primarily as explicit branches, gateways and sub-processes. As dimensions multiply, the process model becomes a map of combinations rather than a model of business intent.

An agentic design instead carries facts in state and calculates current obligations. A new requirement typically adds a policy rule or a capability, not another visual branch through a monolithic process.

2.2 Process diagrams become a second programming language

Large BPMN estates create two executable worlds: process DSL (Domain Specific language) plus application code. Engineers must reason about transactionality, retries, error semantics, code deployment and version compatibility across both. In practice, important logic migrates into scripts, expressions, listeners and external services, so the diagram ceases to be a reliable single source of truth.

2.3 Adaptive work is awkward to model

Modern onboarding, investigations and servicing are not only sequences. They are goal-driven case-management problems: gather sufficient evidence, satisfy applicable obligations, resolve contradictions and then commit a controlled outcome. The next best action can depend on evidence discovered during execution. This maps naturally to a state graph where nodes can calculate obligations or spawn bounded specialist subgraphs.

2.4 BPMN remains useful — but in a different role

Do not create a false dichotomy. BPMN can remain a business communication notation and may continue to run selected stable commodity processes. The strategic shift is to stop treating BPMN engines as the mandatory orchestration substrate for every complex process.
Use BPMN when… Prefer agentic graph when…
Sequence is stable, low-dimensional and already well served. Routing is data/policy-driven and changes frequently.
Process is primarily task hand-off. Process is primarily state/evidence convergence toward a goal.
Few exception types exist. Exceptions are numerous and context-dependent.
No probabilistic reasoning is needed. Deterministic and probabilistic capabilities must coexist.
Replacing it provides little economic benefit. Process-model complexity is already constraining change.

3. What “agent” means in this architecture

The term agent is overloaded. For a regulated bank, the definition must be engineering-grade.

Enterprise agent: a stateful software component responsible for achieving a bounded business objective by observing state, evaluating policy, invoking only authorized capabilities, recording evidence and terminating in a declared outcome or escalation state.

3.1 Five properties of every bank agent

1 · Bounded objective

Example: “establish FATCA/CRS profile” — not “complete onboarding however you think best.”

2 · Typed state

Pydantic/JSON Schema contracts, explicit versioning and clear ownership of every field.

3 · Capability allow-list

Tools are application functions/APIs with authorization; the model never receives arbitrary network access.

4 · Policy envelope

Applicable obligations, entitlements, thresholds, approvals and prohibited actions are externalized from prompts.

5 · Evidence trail

Every decision and action carries inputs, policy version, model version if applicable, result, timestamps and correlation IDs.

6 · Termination contract

Completed, failed, timed-out, awaiting-human, awaiting-client, compensating or escalated are explicit states.

3.2 Four agent classes

Class LLM? Examples Control expectation
D0 — deterministic agent No Eligibility, sequencing, limit checks, routing, timers, policy evaluation. Unit-testable, reproducible, same state + same policy → same result.
D1 — deterministic agent using model-derived facts Not for decision Tax rule evaluation after an LLM extracts fields from a W-8BEN-E. Probabilistic extraction is isolated; final decision is code/rules.
P1 — bounded probabilistic agent Yes Document classification, entity resolution candidate ranking, summarization. Typed output, confidence/evidence, no high-impact write without deterministic validation.
P2 — planning agent Yes Exception investigation or evidence collection strategy. Strict tool allow-list, budget, step limit, approval gates, full trace.

This classification becomes a governance primitive. Most of the core control flow for onboarding should be D0/D1. P1/P2 should be used selectively, where semantic ambiguity creates real value.

4. Architecture principles

1
Determinism is implemented, not prompted. Mandatory rules belong in code/policy/schema/authorization/topology.
2
State over sequence. Store facts, obligations, evidence and decisions. Derive the next action from them.
3
LLMs propose; deterministic controls dispose. A model may recommend, classify or extract. Critical state changes are validated by non-model controls.
4
Small specialist agents beat general agents. Narrow context reduces hallucination surface and simplifies evaluation.
5
Policy version is part of case state. A case must always be explainable against the exact policy bundle that governed it.
6
Every side effect is idempotent. Durable runtimes may replay nodes. Payment/account/client-record writes require idempotency keys and transactional boundaries.
7
Humans are exception authorities, not glue. Human-in-the-loop should be triggered by explicit policy/confidence/risk conditions.
8
Authorization is outside the model. Agent identity, user-delegated authority and tool-level entitlements are enforced by the platform.
9
Evidence before narrative. Persist source facts and provenance; regenerate summaries rather than treating prose as source-of-truth.
10
Design for replay. Given case state, code, policy and model snapshots, the bank must reconstruct why an action occurred.

5. Reference architecture

The recommended runtime is a graph-based case orchestrator, not a free-running swarm. LangGraph is suitable because it exposes state, nodes, edges, persistence, interrupts and subgraphs directly rather than hiding orchestration behind an opaque “autonomous agent” loop.

6. Deterministic agents: replacing BPMN without replacing certainty

A deterministic agent is essentially a stateful domain service with explicit goals and graph semantics. It can observe state, evaluate rules, invoke tools and select transitions, but the selection is code — not sampled model output.

6.1 The equivalence with familiar BPMN constructs

BPMN concept Agentic replacement Implementation
Service task Deterministic graph node Python function / domain service / API tool.
Exclusive gateway Conditional edge Pure routing function over typed state.
Parallel gateway Fan-out / subgraphs Independent nodes with reducer-safe state updates.
Human task Interrupt Persisted graph state + entitlement-checked resume.
Timer Scheduler/event trigger Durable timer service emitting a case event.
Boundary error event Typed exception + retry/escalation edge Error taxonomy, retry policy, dead-letter state.
Call activity Subgraph / agent capability Versioned specialist graph with explicit input/output.
Compensation Compensation command Saga record with idempotent reversal capability.

6.2 Deterministic decisioning pattern

Assume a legal entity wants cash management in Singapore and derivatives in the UK. The decision “is a regulatory classification required?” is not an LLM question. The applicable policy service returns obligations based on typed facts. The graph merely routes to the required specialist agents. 

from pydantic import BaseModel
from typing import Literal

class ClientFacts(BaseModel):
    entity_type: Literal["LEGAL_PERSON", "FINANCIAL_INSTITUTION"]
    incorporation_country: str
    booking_countries: set[str]
    products: set[str]

class Obligations(BaseModel):
    tax_profile: bool
    kyc: bool
    mifid_classification: bool
    mas_classification: bool
    enhanced_due_diligence: bool

def derive_obligations(f: ClientFacts, policy) -> Obligations:
    # Pure deterministic evaluation. No LLM.
    return Obligations(
        tax_profile=True,
        kyc=True,
        mifid_classification=("GB" in f.booking_countries
                              and "DERIVATIVES" in f.products),
        mas_classification=("SG" in f.booking_countries
                            and bool(f.products & {"DERIVATIVES","FX"})),
        enhanced_due_diligence=False,
    )
Explanation
  • ClientFacts and Obligations are typed contracts, avoiding loosely structured workflow payloads.
  • derive_obligations is pure deterministic logic: it does not call an LLM or hidden planner.
  • Jurisdiction and product facts directly determine whether MiFID or MAS obligations are required.
  • In production, the conditions should move into a governed, versioned policy service rather than remain hard-coded.
  • The key control property is reproducibility: same facts + same policy version produce the same obligations.

In production, rules should be externalized into a governed policy bundle rather than hard-coded. The important property is that policy evaluation is referentially transparent: same input facts + same policy version → same output.

6.3 “Next action” does not require an LLM planner

A common misconception is that agentic orchestration requires a model to choose the next node. LangGraph supports conditional edges defined by ordinary Python. A deterministic supervisor can calculate which obligations are still open and dispatch the next bounded subgraph. 

def route_open_obligation(state: "OnboardingState") -> str:
    if state.status == "REJECTED":
        return "end"
    if not state.tax.complete:
        return "tax_agent"
    if not state.kyc.complete:
        return "kyc_agent"
    if state.mifid.required and not state.mifid.complete:
        return "mifid_agent"
    if state.has_blocking_exception:
        return "human_resolution"
    return "provisioning_agent"
Explanation
  • The router chooses the next capability only from persisted case state.
  • The ordering is explicit: reject, tax, KYC, MiFID, human exception resolution, then provisioning.
  • BPMN gateways become ordinary conditional edges that can be unit-tested and code-reviewed.
  • Adding a new obligation is a controlled state/policy/routing change rather than another process-diagram permutation.
  • Replaying the same state always selects the same edge.
This is the core answer to “how can agents be deterministic?” The agent runtime is a state machine; the nodes are typed software; the policy evaluation is deterministic; the graph edges are deterministic. The word “agent” changes component responsibility and composition — it does not require stochastic control flow.

6.4 Deterministic agents can still be adaptive

Deterministic does not mean static. An agent may dynamically discover new obligations because state changes. For example, ownership enrichment may reveal a sanctioned nexus. A policy recalculation deterministically adds an EDD obligation to the case. The path changes because the facts changed, not because a model improvised.

7. Probabilistic agents: where frontier models belong

Frontier models such as OpenAI and Claude are most valuable at semantic boundaries: converting messy human-world information into structured candidate facts, or reasoning over evidence where exact algorithms are weak.

7.1 The probabilistic sandwich

Figure 2 · Probabilistic sandwich pattern

The model does not receive unrestricted context. The input gate determines what data is permitted, which model/provider/region may process it, and which tools are exposed. The output gate validates schema, checks evidence, applies confidence thresholds and determines whether the result can update authoritative state.

7.2 Structured output is necessary but not sufficient

LangChain supports structured responses using provider-native schemas or tool calling. OpenAI also exposes JSON-schema-based Structured Outputs, and Anthropic supports schema-defined tools/structured outputs. Schema conformance prevents malformed data; it does not prove the facts are true. Therefore every extracted field should carry provenance. 

class ExtractedTaxFact(BaseModel):
    field: str
    value: str | None
    source_document_id: str
    source_page: int
    evidence_text: str
    confidence: float

class TaxDocumentExtraction(BaseModel):
    document_type: Literal["W8BEN_E", "W9", "CRS_SELF_CERT", "UNKNOWN"]
    facts: list[ExtractedTaxFact]
    extraction_warnings: list[str]
Explanation
  • The LLM is constrained to a Pydantic schema instead of returning free-form prose.
  • Every extracted fact carries document, page, evidence text and confidence for provenance.
  • UNKNOWN document type and extraction warnings are explicit outputs rather than hidden uncertainty.
  • Structured output is still not authoritative; deterministic validation and policy decide what the bank accepts.
  • This makes model output reviewable, traceable and suitable for human escalation.

A downstream deterministic Tax Agent decides whether those facts satisfy policy. It should not ask the LLM “is the customer FATCA compliant?” unless the bank has consciously classified that as a model decision and applied model-risk controls.

7.3 Model portfolio, not model dependency

The model gateway should allow task-specific routing across approved OpenAI and Claude models. The graph calls a logical capability such as extract_tax_document; the platform decides provider/model based on data classification, latency, cost, evaluation score, region availability and resilience. This prevents model names from leaking throughout domain code.

8. Worked example — new-to-bank corporate onboarding

A useful test of the thesis is a regulated process with deterministic controls, uncertain documents, multiple jurisdictions, long-running waits and human exceptions.

8.1 Business objective

“Create a legally usable client relationship and required product accounts only after all applicable policy, tax, regulatory and KYC obligations are satisfied, while minimizing client outreach and manual operations.”

8.2 State model replaces the giant process diagram

class ObligationStatus(BaseModel):
    required: bool = False
    status: Literal["NOT_REQUIRED","OPEN","IN_PROGRESS","PASS","FAIL","WAIVED"] = "OPEN"
    decision_id: str | None = None
    evidence_ids: list[str] = []

class OnboardingState(BaseModel):
    case_id: str
    policy_version: str
    client_version: int
    facts: ClientFacts
    tax: ObligationStatus
    kyc: ObligationStatus
    mifid: ObligationStatus
    mas: ObligationStatus
    provisioning: ObligationStatus
    open_exceptions: list[str] = []
    status: Literal[
        "ACTIVE","WAITING_CLIENT","WAITING_HUMAN","REJECTED","COMPLETED"
    ] = "ACTIVE"
Explanation
  • The state object stores business obligations and outcomes rather than a token position on a process canvas.
  • Each obligation records whether it is required, its current status, the decision and supporting evidence.
  • Waiting, human-review, rejected and completed conditions are explicit lifecycle states.
  • New obligations can be introduced through schema/policy evolution without modelling every end-to-end path.
  • Persisted state enables safe pause, resume, replay and recovery for long-running onboarding cases.

Rather than drawing every legal path, the case carries the status of each obligation. The orchestration graph asks: what is required, what is already satisfied, and what is blocking completion?

8.3 Example runtime flow

The diagram uses two related visual conventions: color shows the kind of control/capability, while the D/P labels show how deterministic or probabilistic the agent is. The label therefore matters more than the word “agent”: a green D0 agent is ordinary deterministic software packaged as an agent capability; a purple P1 agent contains bounded model reasoning.

Legend · How to read Figure 3

Agent / decision classes

D0 Fully deterministic. No LLM is used to make the decision. Rules, policy, exact algorithms or trusted API responses produce the outcome.
D1 Deterministic decision using model-derived facts. An LLM may have extracted or normalized an input fact, but the authoritative decision is still made by code/policy.
P1 Bounded probabilistic specialist. An LLM performs a narrow semantic task such as extraction, classification, ranking or summarization and must return typed output with evidence/confidence.
P2 Bounded planning / investigation agent. The model may choose among allow-listed tools or investigation steps, but operates within step, cost, data and approval limits.
Gate Deterministic validation gate. A code/policy check that accepts, rejects or escalates a P1/P2 result before it can affect an authoritative banking decision or write.
Human Authorized human control. Used where policy requires judgement, delegated authority, maker-checker or explicit exception approval.

Color coding in the runtime graph

Blue — trigger / control entry. Starts or receives the case/event into the controlled runtime.
Green — deterministic execution. D0/D1 policy, routing, validation or transactional capability.
Purple — probabilistic intelligence. Usually a P1 model-backed semantic capability.
Amber — exception / hybrid reasoning. P1/P2 analysis may propose a resolution, but cannot bypass deterministic or human gates.
Red — human interrupt. Execution is durably paused for an authorized human decision.
Navy — terminal / evidence state. Controlled completion with an immutable decision/evidence manifest.

Rule of thumb: D = deterministic authority; P = probabilistic assistance. Moving from P1 to P2 increases the model's freedom to choose intermediate actions, so the required controls become progressively stronger. High-impact banking decisions and irreversible writes should terminate through D0/D1 or an explicitly authorized Human gate.

9. LangGraph / LangChain implementation pattern

LangGraph’s low-level graph model is a better fit for controlled banking orchestration than a generic ReAct loop. LangChain’s higher-level agents can still be embedded for bounded semantic tasks.

9.1 State and deterministic nodes

from typing import TypedDict, Literal
from langgraph.graph import StateGraph, START, END
from langgraph.types import Command, interrupt

class CaseState(TypedDict):
    case_id: str
    policy_version: str
    facts: dict
    obligations: dict
    extracted_facts: dict
    exceptions: list[dict]
    status: str
    audit: list[dict]

def policy_node(state: CaseState):
    obligations = policy_client.evaluate(
        policy_version=state["policy_version"],
        facts=state["facts"],
    )
    return {
        "obligations": obligations,
        "audit": [{
            "event": "OBLIGATIONS_DERIVED",
            "policy_version": state["policy_version"],
            "decision_hash": obligations["decision_hash"],
        }]
    }

def deterministic_route(state: CaseState) -> str:
    o = state["obligations"]
    if state["status"] == "REJECTED":
        return "end"
    if o["tax"]["status"] == "OPEN":
        return "tax"
    if o["kyc"]["status"] == "OPEN":
        return "kyc"
    if any(e["severity"] == "BLOCKING" for e in state["exceptions"]):
        return "human"
    return "provision"
Explanation
  • CaseState is the shared contract used by every node in the graph.
  • policy_node evaluates a specific policy version and records a decision hash for auditability.
  • deterministic_route selects the next edge from obligations and blocking exceptions only.
  • The model is not allowed to decide orchestration; probabilistic agents may contribute facts to state.
  • This separates semantic reasoning from the bank's authoritative control flow.

9.2 Embed a bounded model agent only where needed

LangChain can enforce structured response formats. The model output should be treated as a candidate fact set and validated before authoritative state is updated. 

from pydantic import BaseModel, Field
from langchain.agents import create_agent

class OwnershipExtraction(BaseModel):
    entity_name: str
    ownership_pct: float = Field(ge=0, le=100)
    evidence: str
    page: int
    confidence: float = Field(ge=0, le=1)

ownership_extractor = create_agent(
    model=approved_model_router("ownership-extraction"),
    tools=[read_document_pages],
    response_format=OwnershipExtraction,
    system_prompt=(
        "Extract only ownership explicitly evidenced in the supplied document. "
        "Do not infer missing percentages. Return page and evidence."
    ),
)

def ownership_extract_node(state: CaseState):
    result = ownership_extractor.invoke({
        "messages": [{
            "role": "user",
            "content": f'Extract direct ownership for case {state["case_id"]}'
        }]
    })
    candidate = result["structured_response"]

    # Deterministic post-condition.
    if candidate.confidence < 0.92:
        return {"exceptions": [{
            "code": "LOW_CONFIDENCE_OWNERSHIP",
            "severity": "BLOCKING",
            "payload": candidate.model_dump()
        }]}
    return {"extracted_facts": {"ownership_candidate": candidate.model_dump()}}
Explanation
  • The model agent is deliberately bounded to one task: extracting ownership evidence.
  • Its tool set is restricted to document reading and its response must conform to a typed schema.
  • The prompt forbids inventing missing ownership percentages and requires source evidence.
  • A deterministic confidence threshold creates a blocking exception when evidence is insufficient.
  • The LLM proposes candidate facts; it cannot approve ownership or authorize downstream onboarding actions.

9.3 Human-in-the-loop is an explicit state transition

LangGraph interrupts persist execution state. In bank use, the resume endpoint must authenticate the human, verify entitlement and persist the approval reason independently of the model. 

def human_approval_node(state: CaseState):
    request = {
        "case_id": state["case_id"],
        "action": "APPROVE_OWNERSHIP_EXCEPTION",
        "exception": state["exceptions"][0],
        "required_role": "KYC_APPROVER",
    }

    decision = interrupt(request)

    # On resume, validate authenticated actor metadata supplied by trusted UI/API.
    assert entitlement_service.can(
        actor_id=decision["actor_id"],
        action=request["action"],
        case_id=state["case_id"],
    )

    if decision["decision"] == "REJECT":
        return {"status": "REJECTED"}

    return {
        "exceptions": [],
        "audit": [{
            "event": "HUMAN_APPROVAL",
            "actor_id": decision["actor_id"],
            "reason_code": decision["reason_code"],
        }]
    }
Explanation
  • interrupt creates a durable human checkpoint rather than a generic workflow inbox task.
  • The request carries the precise case, action, exception and required approval role.
  • On resume, the backend independently verifies the authenticated actor's entitlement.
  • Reject and approve outcomes become explicit state transitions with audit evidence.
  • The human decision is therefore attributable, resumable and enforceable as part of the graph contract.

9.4 Assemble the graph

builder = StateGraph(CaseState)

builder.add_node("policy", policy_node)
builder.add_node("tax", tax_subgraph)
builder.add_node("kyc", kyc_subgraph)
builder.add_node("human", human_approval_node)
builder.add_node("provision", provisioning_node)

builder.add_edge(START, "policy")
builder.add_conditional_edges(
    "policy",
    deterministic_route,
    {
        "tax": "tax",
        "kyc": "kyc",
        "human": "human",
        "provision": "provision",
        "end": END,
    },
)

# After each specialist completes, recalculate obligations and route again.
builder.add_edge("tax", "policy")
builder.add_edge("kyc", "policy")
builder.add_edge("human", "policy")
builder.add_edge("provision", END)

graph = builder.compile(checkpointer=production_checkpointer)
Explanation
  • StateGraph composes specialist capabilities while retaining a deterministic control spine.
  • Policy evaluation is the entry point; conditional edges choose the next specialist from current state.
  • Each specialist loops back to policy so obligations can be recalculated as new facts arrive.
  • A production checkpointer makes execution durable across outages and onboarding cases lasting days or weeks.
  • Provisioning reaches END only after the deterministic routing conditions are satisfied.
Engineering note on interrupts/replay: durable execution can restart a node when resuming. Code before an interrupt or retry boundary must therefore be idempotent. LangGraph’s own documentation explicitly warns that side effects before interrupts should be idempotent.

9.5 Idempotent side-effect pattern

def provisioning_node(state: CaseState):
    idem_key = f'{state["case_id"]}:PROVISION:{state["policy_version"]}'

    # API guarantees same idempotency key cannot create a second account.
    response = account_api.create_account(
        request=build_account_request(state),
        idempotency_key=idem_key,
        workload_identity=current_agent_identity(),
    )

    return {
        "obligations": mark_provisioning_passed(
            state["obligations"], response.account_id
        ),
        "audit": [{
            "event": "ACCOUNT_PROVISIONED",
            "idempotency_key": idem_key,
            "downstream_ref": response.request_id,
        }],
    }
Explanation
  • The idempotency key binds the side effect to case, operation and policy version.
  • The downstream account API must guarantee that retrying the same key cannot create a duplicate account.
  • Workload identity lets the platform authorize the agent independently of a model or human user.
  • Downstream request references are persisted into the audit trail.
  • This pattern is essential because durable graphs may legitimately retry a node after failure or restart.

9.6 Do not allow the model to manufacture tool authority

# Bad
@tool
def execute_sql(sql: str): ...

# Better: business capability with constrained schema
class CreateAccountRequest(BaseModel):
    legal_entity_id: str
    booking_location: Literal["SG","GB","HK"]
    product: Literal["CASA","FX","DERIVATIVES"]
    approved_case_id: str

@tool
def create_account(req: CreateAccountRequest) -> AccountResult:
    # Server independently verifies case status + caller identity + policy evidence.
    authorize(req)
    validate_case_ready(req.approved_case_id)
    return core_platform.create(req)
Explanation
  • A raw SQL tool gives a model broad, difficult-to-govern authority and is therefore the anti-pattern.
  • The preferred tool exposes a narrow business capability with a typed request and permitted values.
  • The server independently authorizes the call and verifies that the onboarding case is ready.
  • A model may request a capability but cannot grant itself permission or bypass policy checks.
  • The tool interface becomes a security and control boundary, not merely an integration convenience.

10. Enterprise-grade control architecture

Agentic systems should increase control quality because controls can be centralized, typed and observable rather than spread across workflow expressions and scripts.

10.1 Control hierarchy

Layer Control Example
Identity Workload identity for every agent/subgraph. spiffe://bank/cib/onboarding/tax-agent
Authorization Tool gateway checks capability + data scope. KYC Agent may read screening but cannot provision an account.
Policy Versioned deterministic rule evaluation. EDD required for specific sanctions/PEP conditions.
Schema Input/output contracts. Country codes, legal entity IDs, decision enums.
State Legal transition validation. Cannot transition from TAX_FAIL to READY_TO_PROVISION.
Human Entitlement + maker/checker. High-risk client approval needs independent approver.
Model Provider/task allow-list + evaluation threshold. Only approved model deployment can process confidential client docs.
Data Residency, classification and minimization. China-resident source documents remain within approved region.
Runtime Step budget, timeout, retry, circuit breaker. P2 investigator limited to 8 tool calls before escalation.
Evidence Immutable provenance and hashes. Decision stores source IDs and policy decision hash.

10.2 Policy-as-code contract

Policy should produce machine-readable obligations, not process routes. This is a crucial decoupling. 

{
  "policy_id": "CIB-ONBOARDING-GLOBAL",
  "version": "2026.08.4",
  "effective_from": "2026-09-01",
  "input_schema": "ClientFacts.v7",
  "decision": {
    "obligations": [
      {"type":"TAX_PROFILE","owner_agent":"tax-agent","blocking":true},
      {"type":"KYC","owner_agent":"kyc-agent","blocking":true},
      {"type":"MIFID_CLASSIFICATION","owner_agent":"reg-agent","blocking":true}
    ]
  },
  "decision_hash": "sha256:..."
}
Explanation
  • The policy artifact is explicitly versioned, effective-dated and tied to an input schema.
  • Obligations declaratively state their type, responsible agent and whether they block completion.
  • The decision hash enables exact replay and proves which policy result drove the case.
  • The graph consumes obligations rather than hard-coding every jurisdiction/product process path.
  • Global rules and country deltas can therefore evolve independently under policy lifecycle governance.

The graph does not need to know why MiFID applies. It knows an obligation exists, who owns it and whether it blocks completion. The rule engine can change without redesigning the orchestrator.

10.3 Model risk

In April 2026, the Federal Reserve, OCC and FDIC issued revised guidance on model risk management, superseding SR 11-7. The architecture should assume model-risk expectations around development/use, validation/monitoring, governance and third-party models may apply to material AI components. The safest design minimizes the number of material control decisions made by a model and makes every model contribution measurable and replaceable.

Anti-pattern: “temperature = 0” is not a control. It may reduce sampling variability, but it does not convert a language model into a policy engine, guarantee factual correctness or guarantee identical outputs across provider/model changes.

The bank needs three observability layers on one trace: technical execution, business progress and model behavior.

  • Evaluation cohort and benchmark score for the deployed prompt/model combination.

11.3 Business activity monitoring improves

Because obligations are first-class state, operations no longer needs to infer progress from workflow node names. Dashboards can directly answer: percentage of cases blocked on client evidence, EDD volume by policy reason, median time from tax evidence receipt to decision, model low-confidence rate, human override rate, and policy-version impact.

12. Testing and assurance

The most important engineering advantage of this architecture is that it allows different assurance techniques for deterministic and probabilistic components.

12.1 Deterministic assurance

Unit & property tests

Every transition, policy adapter and validator. Property: no state can reach READY_TO_PROVISION while a blocking obligation is OPEN/FAIL.

Golden case replay

Historical cases are replayed against a proposed graph/policy version and diffs are reviewed before deployment.

Contract tests

Tool schemas, API error taxonomy, idempotency and authorization.

Failure injection

Timeouts, duplicated events, stale state, downstream outages, partial writes, resume-after-crash. 

def test_never_provision_with_open_blocking_obligation():
    for case in generated_case_states():
        if any(o["blocking"] and o["status"] != "PASS"
               for o in case["obligations"].values()):
            assert deterministic_route(case) != "provision"
Explanation
  • This is a property-style test over many generated case states rather than only hand-written happy paths.
  • Its invariant is simple: any open blocking obligation must make provisioning unreachable.
  • The test exercises the deterministic router directly, without needing a model or full integration environment.
  • It detects routing regressions when new obligation types or statuses are introduced.
  • Deterministic agent graphs make this kind of exhaustive control testing practical.

12.2 Probabilistic assurance

  • Task-specific benchmark datasets, not generic model benchmarks.
  • Field-level precision/recall for extraction; false-positive/false-negative costs documented.
  • Groundedness: every material extracted fact must point to evidence.
  • Robustness across document layout, language, poor scans and adversarial text.
  • Human override and downstream rejection rates monitored after deployment.
  • Champion/challenger testing across approved OpenAI/Claude deployments.
  • Model or prompt change cannot silently change a control outcome; it must pass replay gates.

12.3 End-to-end invariant tests

Traditional workflow testing often enumerates paths. Agentic testing should focus more on invariants over state: 

INVARIANT 1: no account exists unless case.status == COMPLETED
INVARIANT 2: every completed case has a policy_version and evidence_manifest
INVARIANT 3: no model can directly set a human approval field
INVARIANT 4: every authoritative fact has provenance
INVARIANT 5: every side-effect tool call has an idempotency key
INVARIANT 6: no cross-border model call violates the data residency decision
Explanation
  • These invariants are non-negotiable banking controls that apply regardless of which path the case followed.
  • They prevent completion without required policy versioning, evidence and provenance.
  • They explicitly prohibit a model from setting fields that represent human approval.
  • They require idempotency for side effects and enforce data-residency constraints around model calls.
  • Control-as-code is testable continuously, rather than relying on visual inspection of every BPMN path.

This is a more scalable assurance approach than proving thousands of graphical paths individually.

Every production agent should be deployed with a machine-readable manifest so architecture, security and operations can discover its authority.

Explanation
  • The manifest treats an agent as a governed production workload with a versioned contract.
  • Class D1 identifies a deterministic decisioning agent that may consume model-derived facts.
  • Allow-listed tools, models and policy namespaces constrain authority and blast radius.
  • Data classification, human interrupts and execution budgets are declared up front.
  • Named ownership and versioning create operational accountability and controlled deployment.

13.3 Why use LangGraph rather than only LangChain’s generic agent loop

LangChain’s high-level agent abstraction is useful for contained P1/P2 tasks. LangGraph should remain the outer execution substrate when exact topology, state, durable execution, interrupts, subgraphs and deterministic routing matter. LangChain itself now builds its high-level agent runtime on LangGraph, which reinforces this layering.

14. Migration strategy from BPMN

The bank does not need a “big bang BPMN removal” program. Migration should be capability-led and should preserve outcomes while progressively moving control to state/policy/agent abstractions.

14.1 Four stages

Stage What changes Risk
1 · Agent inside BPMN Use bounded AI agents for document extraction/summarisation, invoked as workflow services. Low. Proves model gateway and evaluation.
2 · Sub-process replacement Replace one complex BPMN sub-process with a LangGraph subgraph; BPMN remains parent. Moderate. Introduces durable graph operations.
3 · Agentic case orchestrator LangGraph owns case state and obligations; existing BPMN processes become tools/legacy adapters. Strategic transition point.
4 · BPMN as optional notation New complex processes use agent graphs by default; BPMN retained only where it is the simplest fit. Requires new architecture/engineering standards.

14.2 How to decompose an existing BPMN model

  1. Extract all data fields carried by process variables → define canonical typed case state.
  2. Extract all gateways and expressions → classify each as policy, routing, authorization or error handling.
  3. Move business eligibility/obligation logic into policy-as-code.
  4. Turn service tasks into business capabilities/tools with idempotency contracts.
  5. Group cohesive tasks into specialist agents/subgraphs by business objective.
  6. Convert human tasks into named interrupt contracts with required roles and reason codes.
  7. Convert timers/errors into explicit runtime events and state transitions.
  8. Define completion invariants; prove old and new execution against a golden historical case set.
Migration criterion: do not compare diagrams node-for-node. Compare business invariants, obligations, outcomes, evidence and SLAs. An agentic graph may be structurally different while being behaviorally equivalent — and much simpler.

15. Recommendation

Adopt stateful agentic orchestration as the strategic architecture for complex client, risk, compliance and servicing processes. Use LangGraph as the explicit graph/runtime layer; LangChain and frontier models as bounded intelligence components. Treat deterministic agents as first-class agents and require control decisions to remain outside LLM prompts unless explicitly approved as model decisions.

Guardrails

Require

Typed state, policy versioning, deterministic routing for controls, tool allow-lists, idempotency, evidence lineage, durable checkpoints, human entitlements, model gateway, evaluations, full observability.

Prohibit by default

General agent with broad APIs, direct database tools, model-controlled entitlements, prompt-only policies, unbounded loops, unvalidated free-text downstream payloads, silent model upgrades, hidden cross-region model calls.

Final position: the choice is not “BPMN determinism versus agentic probabilism.” A well-designed agentic platform can be more deterministic where determinism is required, while adding probabilistic intelligence only where the business problem demands it. That is the architecture that can credibly replace BPMN for the next generation of banking processes.

Appendix A — Decision matrix: should this node use an LLM?

Question If YES If NO
Can the requirement be expressed completely as explicit rules over trusted data? Use D0/D1, no LLM for the decision. Continue.
Is the input unstructured language/image/document content? P1 may extract/classify into typed candidate facts. Probably deterministic.
Would two competent humans reasonably disagree? P1/P2 may assist, with confidence/evidence and review threshold. Prefer deterministic implementation.

Appendix B — Example state-transition validator

LEGAL_TRANSITIONS = {
    "ACTIVE": {"WAITING_CLIENT","WAITING_HUMAN","REJECTED","COMPLETED"},
    "WAITING_CLIENT": {"ACTIVE","REJECTED"},
    "WAITING_HUMAN": {"ACTIVE","REJECTED"},
    "REJECTED": set(),
    "COMPLETED": set(),
}

def validate_transition(before: CaseState, after: CaseState):
    if after["status"] not in LEGAL_TRANSITIONS[before["status"]]:
        if after["status"] != before["status"]:
            raise IllegalStateTransition()

    if after["status"] == "COMPLETED":
        blocking = [
            x for x in after["obligations"].values()
            if x["blocking"] and x["status"] != "PASS"
        ]
        if blocking:
            raise InvariantViolation("Cannot complete with blocking obligations")

        if not after.get("evidence_manifest_id"):
            raise InvariantViolation("Completion requires evidence manifest")
Explanation
  • Legal lifecycle transitions are encoded explicitly and can be tested independently of individual agents.
  • The validator rejects any illegal state transition even if a node or model proposes it.
  • COMPLETED is impossible while a blocking obligation remains unresolved.
  • An evidence manifest is mandatory before the case can complete.
  • This validator acts as a final deterministic guardrail around all graph state writes.
